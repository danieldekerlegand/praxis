## Codebase Patterns

- **The seed library notebooks ARE the released artifact.** `checks.publish_graded_cells()`
  writes nbgrader's `generate_assignment` output to `topic_path()`, so `notebooks/**.ipynb`
  carry no reference solutions. The answer key is the `<slug>.checks.json` sidecar beside
  them — so anything copying a notebook DIRECTORY carries the key. Copy files, not dirs.
- **`checks.graded_cells()` does not find every graded cell.** It matches only
  `metadata.praxis.extension == "checks"`. nbgrader's companion autograder-tests cell
  (`grade_id` `<id>-tests`, `grade+locked`, no praxis namespace) is NOT in that list — and
  its assertions are the answer. Any "is this safe to show?" check needs the nbgrader flags
  too, which is what `lite._graded()` does. Measured: 24 seed notebooks carry 24 such cells
  with their assertions in plain text, so the shipped library's "hidden tests" are visible
  in any full-notebook render. Relevant to US-3.
- **The system `python3` here is 3.14 with the core deps; there is no `.venv`.** The full
  suite takes ~6 min. Two concurrent `pytest -q tests/` runs roughly double that — run one.
- **`npm run build` needs `npm --prefix ui ci` first** in a fresh worktree (no node_modules).
- Network is available (pypi, npm, jsdelivr) but the framework Python's SSL has no CA
  bundle — `urllib` fails with CERTIFICATE_VERIFY_FAILED while `curl` works. That is why
  `praxis.lite index` takes `--lock <file>`.

## US-1 — A JupyterLite site that runs a released tutorial with no local Python (done)

Commit d4ecb30.

**What was built**

- `praxis/lite.py` — the staging half of the adoption. Pins (`JUPYTERLITE_CORE` 0.8.3,
  `JUPYTERLITE_PYODIDE_KERNEL` 0.8.5, `JUPYTER_SERVER` 2.14.2 build-time only) live here
  and nowhere else; the build script reads them back via `python3 -m praxis.lite pins`.
  `browser_notebook()` strips every graded region, `leak_failures()` re-inspects the
  artifact after stripping, `stage_contents()` raises rather than writing a leak,
  `requirements()` triages imports against the vendored Pyodide index.
- `praxis/data/pyodide-packages.json` — vendored `pyodide-lock.json` `imports` map (304
  importable names) + stdlib names, for Pyodide v314.0.5 / CPython 3.14.2. Regenerate with
  `python3 -m praxis.lite index --pyodide v314.0.5 [--lock <file>]`.
- `scripts/build-jupyterlite.sh` (`--check` / `--force`), `make build-lite`, wired into
  `make build` (before `build-ui`) and `make bundle`. Stamp-guarded: a re-run with the site
  already staged for the current pins took 0.34s.
- `docs/reference/jupyterlite.md` (linked from `docs/README.md`, cross-referenced from
  `docs/reference/packaging.md`) — states the runtime/gate split explicitly.
- `tests/test_lite.py` — 16 tests. The built-site test skips itself when no site is staged,
  the same discipline the launcher tests use for the launch extra.

**Learnings for future iterations**

- The pinned kernel loads Pyodide from `cdn.jsdelivr.net/pyodide/v314.0.5/full/`, so a
  FIRST run needs network even though nothing is installed locally. Documented, not fixed —
  `jupyter lite build --pyodide <dist>` is the offline path and adds ~250 MB. If US-2's
  "zero terminals" demo is run offline, expect the kernel not to start; that is this, not a
  bundling bug.
- The site is 72 MB. Do NOT put it in `ui/dist` — that is embedded into the Rust binary at
  compile time. Serve it from `src-tauri/resources/` as a Tauri **resource** (the pattern
  `praxis-runtime` + `tauri.embedded.conf.json` already established). US-2 should follow
  that, plus a small static file server in `library.rs`.
- `jupyterlite-core` needs `jupyter-server` installed at BUILD time or the contents addon
  fails with "jupyter-server is not installed. You cannot add custom content to
  jupyterlite." — hence the third pin.
- 5 of the 101 "available" notebooks have zero Python code cells (R/Quarto topics — their
  content is conceptual). "Available" means "nothing it imports is missing", not "it has
  code to run".
- `window.jupyterapp` is NOT exposed by JupyterLite's lab page; drive it through the menu
  (`Run` → `Run All Cells`) and read `.jp-InputPrompt` / `.jp-OutputArea-output` from the
  DOM.

## US-2 — Bundle it so first run is one launch, not two terminals (done)

**What was built**

- `src-tauri/src/lite.rs` — the shell serves the site itself: find it (`$PRAXIS_LITE_SITE`
  → `<resources>/jupyterlite` → a checkout's `src-tauri/resources/jupyterlite` above the
  binary or the cwd), read `praxis-lite.json`, and serve the tree read-only on a **second**
  loopback port. ~60 lines of `std::net`, no new crate. `..` is refused rather than
  normalized and the *canonical* path is re-checked against the root (a symlink planted in
  an asset tree is how a normalizing server still serves `/etc/passwd`); missing → 404,
  escape → 403, non-GET/HEAD → 405. `lite_status` is a second Tauri command, deliberately
  independent of `launcher_status`.
- `src-tauri/tauri.lite.conf.json` + `make bundle`/`bundle-app` + `scripts/bundle-macos.sh`
  — the site rides into the bundle through an **overlay** config for the same reason the
  embedded runtime does (a `bundle.resources` entry naming missing build output fails every
  build). The release script reports which runtime it is shipping:
  `bundle: lite 101/245 tutorials runnable in the browser (jupyterlite 0.8.3, pyodide v314.0.5)`.
- `praxis/lite.py` — the manifest now carries the labels a shell with **no Python** needs:
  `domains: [{dir,name,title,blurb}]` and `domain`/`title` on every tutorial. `library_index()`
  returns `Source(rel, path, domain, title)`; `library_sources()` is the old pair view over it.
  `domain_label` / `topic_title` restate `launcher.app._short` / `_topics_for`'s rules
  (the site is built by `.lite-venv`, which has no FastAPI) and a test pins them together.
- `ui/src/lite.ts` + `ui/src/LiteLibrary.tsx` + `App.tsx` — the reader's third tab is now
  **run it here** (was *live in Lab*): the JupyterLite URL in the same pane. A tutorial
  Pyodide cannot serve gets a pane naming the missing modules and pointing at `praxis-lab`
  as the authoring path, never an empty iframe. With the launcher down, `LiteLibrary` draws
  the library out of the manifest and names what it therefore cannot do.
- README: the learner path is now "open the app, pick a tutorial, hit run"; the two-terminal
  block survives under **### The contributor/authoring path**, labelled. `docs/reference/packaging.md`
  gained *The tutorial runtime in the bundle*; `docs/reference/jupyterlite.md` gained
  *In the app: who serves it, and what happens without Python*.
- `Makefile` and `README.md` joined the python job's path predicate in `.chief/verify.sh`
  **and** `.github/workflows/ci.yml` — `tests/test_packaging.py` now pins what `make bundle`
  ships and what the README asks a learner to do, so a lone edit to either must reach the gate.

**Learnings for future iterations**

- **The iframe question is settled**: JupyterLite runs fine inside an iframe on a different
  loopback origin — kernel starts, cells execute, no page errors. No COOP/COEP headers are
  needed (and must NOT be added: the kernel fetches Pyodide from jsdelivr, which
  `require-corp` would block).
- `curl` normalizes `..` out of a URL before sending, so a traversal probe with curl proves
  nothing. Use a raw socket.
- Two Tauri `--config` overlays compose (`tauri build --config a.json --config b.json`);
  the CLI merges them in order and each names a different `bundle.resources` key. The lite
  overlay was verified by a real bundle; the lite+embedded pair is by the CLI's documented
  merge, not by a build here.
- This environment has **no screen-recording or accessibility permission**, so no window
  screenshot and no `AXRaise`. Driving `ui/dist` in headless chromium is the equivalent
  evidence for anything the frontend does; only the Tauri-only surface (`invoke`) needs the
  window.
- `praxis-lite.json` is a *build* artifact: changing what `manifest()` writes means
  `scripts/build-jupyterlite.sh --force` (the stamp only tracks the pins), not just a test run.

## US-3 — Keep the gate's authority out of the browser (done)

**The question US-1 and US-2 left open**

JupyterLite made the *runtime* a place the learner controls completely. That sharpened a
question the repo had answered informally: which process holds the answer key, and what is
allowed to cross into a browser? Two real holes were found while answering it — one flagged
by US-1's own Codebase Patterns note, one new.

**What was built**

- `docs/reference/gate-authority.md` — the one place. Trust table (Python core = trusted;
  the Rust shell trusted as a *process* but holds no gate state, on purpose, because
  "graded" is defined once in `praxis/checks.py`; webview and site untrusted), the four
  artifacts that may cross with one filter each, where grading happens and why not in
  Pyodide, and that unlocks stay derived. Linked from `docs/README.md`;
  `docs/reference/jupyterlite.md` now **defers** to it rather than restating it — two
  statements of one boundary drift.
- `checks.learner_answer()` — `learner_check()`'s **inbound twin**, and the hole nobody had
  named. Outbound was guarded; inbound was "we happen to only read two keys". Now
  `ANSWER_FIELDS = ("check_id", "answer")` is read and `VERDICT_FIELDS` (`passed`,
  `outcome`, `detail`, `graded_by`, `graded`, `locked`, `unlocked`, `state`) is **refused
  400** rather than ignored — a client that sends a verdict believes it grades. The list is
  pinned to cover every key of the endpoint's own reply, so echoing a response back is
  refused by construction.
- **`/render/<rel>` now runs `lite.browser_notebook()`.** This was the real leak, and it was
  a *rendered page*, not the new site: a full render of a gated notebook showed the graded
  cells verbatim. The rendered pane is HTML in a browser with devtools — the same untrusted
  surface the site is — so it gets the same filter, and one filter serves both.
- `src-tauri/src/lite.rs` refuses any `*.checks.json` target with **403** before resolving
  it. The site containing no answer key is a property of the last build; this is a property
  of the server.
- `tests/test_gate_authority.py` (20 tests, needs no launch extra) + 4 API tests in
  `tests/test_launcher_api.py`. The doc joined the python path predicate in **both**
  `.chief/verify.sh` and `.github/workflows/ci.yml`, because the test reads it.

**Observed — the leak, measured on the shipped library**

Markup has to be stripped before "is the answer on this page?" is measurable: nbconvert's
classic template highlights code into `<span>`s, so `assert x == 3` is never one string in
the HTML source. Searching the *visible* text:

| in a full `/render` of the 24 gated seed notebooks | before | after |
|---|---|---|
| graded cells readable | **162 / 168** | **0 / 168** |
| `assert` lines readable | **146 / 146** | **0 / 146** |
| notebooks affected | **24 / 24** | **0 / 24** |

**Gates**

- `python3 -m pytest -q tests/` — **1150 passed, 1 skipped** in 379.05s (baseline 1127; the

- `cargo build` green; `cargo test` **12 passed** (was 11).

- `python3 scripts/validate_nbgrader.py notebooks` → 24 notebooks, 0 failures.

**Learnings for future iterations**

- **A substring search over rendered HTML proves nothing about code.** nbconvert highlights
  it into spans. Strip tags and unescape entities first, then search — that is the only way
  a "does this page show the answer?" assertion means anything. `visible_text()` in
  `tests/test_gate_authority.py` is the helper.
- **The seed library is a better fixture than a constructed one for gate tests**: 24 real
  gated notebooks with their keys beside them, no model, no `construct` job, ~1.6s for the
  whole file. `study_model(rel)` works on them directly with `PRAXIS_PROGRESS_DIR` pointed
  at a tmp dir.
- The outbound boundary had a name (`learner_check`) and the inbound one did not, which is
  exactly why the inbound one was weaker. If you add a surface, ask what the *return* path
  is allowed to say.
- `praxis/lite.py` imports only `curriculum` — it is safe to import from `launcher/app.py`
  and from the `.lite-venv` build alike. Keep it that way; `praxis.checks` pulls `llm` and
  nbgrader and would break the site build.
